Recipe push: adopting an existing content item BY NAME no longer strands the push on a template-mismatched name-twin. A tenant that has seen partial/rolled-back installs can hold an item at a recipe's exact path (same parent, same name — e.g. `<contentItemsRoot>/features`) whose live template belongs to a different site handle's GUID family, or dangles after its own install was rolled back — rollback is best-effort, so a failed `deleteItem` strands exactly these twins. Every adoption seam (the planner's path-hit and sibling-byName adoption, the authoring client's `idempotencyCheck` pre-check and already-exists fallback) was template-blind for content items, so the twin was adopted untouched and the recipe aborted on its first field write with the baffling `Cannot find a field with the name Title` (field names resolve against the item's live template). A CreateOnly, non-folder-class CreateItem whose expected template resolves to a live itemId now adopts-and-RETEMPLATES: the twin is realigned to the recipe's template via Authoring `updateItem`, then the create's fields are seeded — the name is the recipe's own, so the 0.32.5 guard's "decline and create fresh" would just collide back into the conflict, and like the 0.33.0 folder adoption the realignment is lossless for recipe-seeded items (deterministic identity, field values keyed by field id — values under the foreign template's ids are orphaned either way, and the item's GUID is preserved for existing layout references). Folder-class adoption (0.33.0) and the datasource rebind guard (0.32.5) are unchanged; a rejected retemplate surfaces an actionable error naming the colliding item's path and both templates. Self-healing on the next push — no tenant cleanup needed.
